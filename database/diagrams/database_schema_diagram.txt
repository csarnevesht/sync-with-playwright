🗄️ SUPABASE DATABASE SCHEMA DIAGRAM
=====================================

📋 SCHEMA OVERVIEW
------------------
This database schema is designed to store and manage Dropbox account information, 
application files, and person details extracted from insurance applications.

⚠️  LEGACY TABLES NOTE
----------------------
The applications, household_members, dropbox_account_applications, and 
dropbox_account_household_members tables are legacy structures that may not exist 
in your current database. They are included here for reference but are not actively 
used in the current system.

📊 DATABASE TABLES
==================

🔵 CORE TABLES (Currently Active)
--------------------------------

1. 📁 dropbox_accounts (Core Table)
   ├── id: SERIAL PRIMARY KEY
   ├── folder: VARCHAR(255) NOT NULL UNIQUE
   ├── first_name: VARCHAR(100)
   ├── middle_name: VARCHAR(100)
   ├── last_name: VARCHAR(100)
   ├── total_files: INTEGER DEFAULT 0
   ├── processed_files: INTEGER DEFAULT 0
   ├── failed_files: INTEGER DEFAULT 0
   ├── processing_timestamp: TIMESTAMP WITH TIME ZONE
   ├── created_at: TIMESTAMP WITH TIME ZONE DEFAULT NOW()
   └── updated_at: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

2. 👤 person_info (Core Table)
   ├── id: SERIAL PRIMARY KEY
   ├── first_name: VARCHAR(100)
   ├── last_name: VARCHAR(100)
   ├── date_of_birth: DATE
   ├── gender: VARCHAR(50)

3. 📄 dropbox_account_application_files (Core Table)
   ├── id: SERIAL PRIMARY KEY
   ├── file_name: VARCHAR(255) NOT NULL
   ├── file_path: TEXT
   ├── application_type: application_type DEFAULT 'Unknown'
   ├── status: application_status DEFAULT 'Processed'
   ├── owner_id: INTEGER REFERENCES dropbox_account_application_info(id)
   ├── joint_owner_id: INTEGER REFERENCES dropbox_account_application_info(id)

   ├── lm_studio_model_used: VARCHAR(100)
   ├── processing_duration_seconds: DECIMAL(10,3)
   ├── dropbox_account_id: INTEGER REFERENCES dropbox_accounts(id)
   └── created_at: TIMESTAMP WITH TIME ZONE DEFAULT NOW()

🔗 TABLE RELATIONSHIPS
======================

1. dropbox_accounts ↔ dropbox_account_application_files
   └── One-to-Many: Each Dropbox account can have multiple application files
       via dropbox_account_id foreign key

2. person_info ↔ dropbox_account_application_files (Owner)
   └── One-to-Many: Each person can be the owner of multiple application files
       via owner_id foreign key

3. person_info ↔ dropbox_account_application_files (Joint Owner)
   └── One-to-Many: Each person can be the joint owner of multiple application files
       via joint_owner_id foreign key

4. dropbox_accounts ↔ applications (Legacy)
   └── Many-to-Many: Legacy relationship through dropbox_account_applications junction table

5. dropbox_accounts ↔ household_members (Legacy)
   └── Many-to-Many: Legacy relationship through dropbox_account_household_members junction table

🎯 CURRENT SYSTEM FOCUS
=======================

The current system primarily uses these three core tables:
1. dropbox_accounts - Stores account metadata and processing stats
2. person_info - Stores owner and joint owner information
3. dropbox_account_application_files - Stores processed application file data with relationships

The legacy tables (applications, household_members, and junction tables) are 
included for backward compatibility but are not actively used in the current system.
